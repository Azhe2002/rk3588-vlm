## 总体判断

这项工作的现象有工程价值，实验也已经明显超过普通项目报告：有两个模型、分辨率梯度、温度、措辞、模糊、缩放、静态图和实时帧等多组干预，并保留了大部分原始日志与运行脚本。最值得保留的主线是：**在当前 RK3588S + llama.cpp + SmolVLM 的具体实现中，单词级 yes/no 输出的比例对输入链路、采集分辨率、图像处理和措辞非常敏感，而输出语义与输出形态可能分离。**

但当前版本还不适合直接投稿。主要问题不是文字表达，而是：

1. “格式合规率”和“输出 Yes 的比例”被混用，部分表格的主指标算错；
2. 单次会话内的连续帧被当作独立样本做显著性检验，存在伪重复；
3. 多处机制性和因果性措辞超过了当前对照能够支持的范围；
4. 一份关键基线日志被同名重跑覆盖，论文数值与仓库现有文件不一致；
5. 论文所称的部分复现材料实际未入库。

建议将当前稿定位为一篇**实现相关、探索性的边缘端案例研究**。先完成指标和数据审计，再增加跨会话随机区组复现，最后再讨论“描述先验”“必要条件”和模型规模机制。

## 一、投稿前必须修正的问题（P0）

### 1. 重新定义并重算三个互相独立的指标

论文 §3.6 声称主指标是原始输出为 yes/no 单词的比例，但当前代码中：

- `result_parser.c::parse_yes_no()` 会在一整行中搜索 `yes` 或 `no` token，并不验证整条输出只有一个单词；
- `analyze.py` 的 `strict_yes_rate` 只把程序结果为 `YES` 的轮次计为 1，把合规的 `No.` 计为 0；
- 因而 `strict_yes_rate` 实际更接近“可被解析为 Yes 的比例”，不是“格式合规率”；
- 在目标存在、模型全答 Yes 的组中，两者数值碰巧相同，掩盖了这个问题；模糊组和 D@320 立即暴露了混用。

建议固定以下口径，并生成一份机器可读 CSV：

| 指标 | 建议定义 | 是否依赖真值 |
|---|---|---|
| `format_exact` | 原始输出严格等于 `yes` 或 `no`；是否允许句点需预注册 | 否 |
| `format_word` | 去首尾空白及允许的末尾标点后，整条输出为单个 `yes`/`no` | 否 |
| `semantic_label` | 输出语义为 yes/no/unknown | 否 |
| `semantic_correct` | `semantic_label` 与人工标注真值一致 | 是 |
| `yes_rate` | `semantic_label=yes` 的比例 | 否，不能称准确率 |

如果论文继续把 `Yes.` 当作合规，推荐 `format_word` 使用锚定整条输出的正则，例如 `^\s*(yes|no)[.!]?\s*$`，并明确允许哪些标点。`parse_yes_no()` 可保留为工程解析器，但不要再称其为“严格格式判定器”。

按仓库现有日志重算后，下列位置必须更正：

| 论文位置 | 当前写法 | 日志支持的口径 | 应改为 |
|---|---|---|---|
| §4.9，σ=3 | 格式遵循 28/32 | 单词 32/32；语义 Yes 28/32 | 格式 100%，Yes 率 87.5% |
| §4.9，σ=7 | 格式遵循 0/30 | 全部为单词 `No.` | 格式 100%，Yes 率 0% |
| §4.9，σ=15 | 格式遵循 0/28 | 全部为单词 `No.` | 格式 100%，Yes 率 0% |
| §4.10，σ=4 | “严格”29/31 | 单词 31/31；Yes 29/31 | 格式 100%，Yes 率 93.5% |
| §4.10，σ=5 | “严格”10/31 | 单词 31/31；Yes 10/31 | 格式 100%，Yes 率 32.3% |
| §4.10，σ=7/15 | 格式 0% | 单词均为 100% | 格式 100%，Yes 率 0% |
| §4.11，D@320 | “D 严格”4/33 | 单词 33/33；Yes 4/33 | 格式 100%，Yes 率 12.1% |

这项修正不会推翻“模糊后句子输出消失”的观察，反而使结论更清楚：**σ=1–15 的所有模糊组都是 100% 单词输出；随着 σ 增大，变化的是语义 Yes 率，而不是格式率。** 因此原文关于 σ=3/4/5/7/15 的 Fisher p 值也要按正确终点重算并重新命名。

### 2. 修复实验 5 A 基线的数据覆盖和不可复现问题

论文 §4.4 报告 A 组为 `15/33 (45%)`，但当前仓库的 `experiment/data/exp5_A_256_640_ctrl.log` 实际是：

- 32 轮；
- 3 个单词 `Yes.`；
- 29 个完整句子；
- 即格式率 `3/32 = 9.4%`。

Git 历史提交 `38b000f` 中的旧版同名日志则确实是 `15/33`，后续提交 `29c639f` 用一次 `3/32` 重跑覆盖了它。论文中的 B–F 组 p 值显然是相对旧版 `15/33` 基线计算的，因此当前检出结果无法从工作树直接复现。

必须采取以下措施：

1. 从 Git 历史恢复旧日志，但保存为唯一名称，例如 `20260811_session01_exp5_A_...log`；
2. 将当前 `3/32` 保存为另一个 session，而不是覆盖；
3. 重新生成所有 B–F 对比和多重检验校正；
4. 给每次运行记录 session、开始时间、模型/投影文件 SHA-256、二进制 SHA-256、完整参数和输出文件 SHA-256；
5. 日志文件名必须含 session/run ID，脚本发现同名文件时应拒绝覆盖。

恢复后，45% 可以作为一轮会话结果保留，但不能再写成稳定基线；现有证据显示同配置至少出现过 9%、36%、45% 和 67%，这本身就是需要建模的会话效应。

### 3. 把 session/run 作为实验重复单位，不能把连续帧全部当作独立样本

当前每组的 27–45 个样本来自同一摄像头场景、同一次 server 运行和时间上相邻的帧。相邻帧高度相关，且论文已经观察到跨会话基线从 36% 到 67% 大幅变化。直接对帧计数做 Fisher 精确检验隐含了样本独立假设，会低估不确定性并让 p 值偏小。

最低限度的修正是：

- 明确把现有 p 值标为“探索性、未校正帧级比较”；
- 报告比例的 Wilson 95% 置信区间和效应量，不只报告 p 值；
- 对措辞、温度和多个 σ 比较做 Holm 校正；
- 删除“p<0.01 因而确认机制”式表达。

更可靠的下一轮设计是：每个条件至少跨 5–10 个独立 session 重复；每个 session 内采用随机区组或交错顺序（如 A–处理–A），以 session 为聚类单位。可用二项混合效应模型：

```text
format_word ~ model * resolution + temperature + wording + blur + (1 | session)
semantic_correct ~ model * resolution + temperature + wording + blur + (1 | session)
```

如果使用完全配对的同帧变体，则可加入 `(1 | frame)`，或使用配对置换/McNemar 检验。session 数很少时，优先报告每个 session 的原始比例和聚类 bootstrap，不要用复杂模型制造虚假精度。

### 4. “语义正确”“感知失败”和“诚实回答”需要独立真值

当前研究几乎只有一个目标存在的正样本场景。因此 `yes_rate` 在该场景中可以暂时作为目标存在性正确率，但必须先明确：风扇是否确实满足每一种措辞的完整命题，尤其是 “in the center”。仅靠关键词启发式不能证明感知正确。

以下表述需要降级：

- “语义判断 100% 正确”改为“输出语义 100% 为肯定，且与人工设定的目标存在标签一致”；
- “低分辨率感知失败”“看不清”“诚实 No.”改为“输出转为 No；是否由感知失败导致尚未被独立感知测量验证”；
- “感知成功 + 信息过载”改为“肯定语义 + 句式输出”这一可观测行为状态；
- “感知/推理未受损”改为“本单一正样本任务未观察到肯定语义下降”。

应增加：多个正/负场景、多个目标类别、目标不在中心的反例、无图/纯文本基线、遮挡或空白图基线。否则 D 措辞把 320 下答案从 Yes 翻为 No，也可能是文本模板先验变化，而不一定是视觉证据阈值改变。

### 5. 静态图与实时帧的对照尚不能推出“逐帧变化是必要条件”

§4.12 的无缓存复核排除了 prompt cache，但没有隔离以下差异：

- 静态组反复使用一张旧 JPEG，实时组使用一串不同 JPEG；
- 两组不是相同的图像字节，也没有逐帧配对；
- 当前静态日志是对同一输入在 temperature=0.1 下重复采样，30 次输出不是 30 个独立图像样本；
- 论文写“同一图像内容”“同日同帧”，但现有脚本实际是顺序运行的不同帧/不同组；
- `run_static_nocache.py` 会覆盖同一个 `exp_static_nocache.log`，仓库当前只保留高细节静态图的 30 轮，论文表中的低细节静态组日志已不可见。

更严格的验证方案：

1. 先采集 K 张实时帧并冻结原始 JPEG 字节；
2. 每张图分别经“实时程序请求路径”和“静态 HTTP 请求路径”提交，保证 payload、prompt、temperature、max_tokens、cache 配置完全一致；
3. 另构造同一基础帧的 JPEG 质量、像素噪声或帧差梯度序列，量化多大的变化开始改变格式；
4. 用 temperature=0 做确定性主分析，再用多个显式随机种子估计采样效应；
5. 使用配对统计，而不是把 30 次重复请求与 33 张连续帧做普通 Fisher 检验。

在完成该实验前，建议结论改为：**“固定单图重复请求与在线相机帧序列呈现不同输出形态；差异可能与图像身份、编码、帧间变化或请求路径有关。”**

### 6. 模糊实验存在 `videoconvert` 混杂，缩放/裁剪也未完全隔离“细节量”

所有 gaussianblur 组都使用：

```text
videoconvert ! gaussianblur sigma=N ! videoconvert
```

但 σ=0 基线没有相同的两次 `videoconvert`。因此 σ=1 即从 67% 跳到 100%，可能来自模糊，也可能来自颜色格式、量化、色度采样、JPEG 输入或两次转换的组合。必须增加 `videoconvert ! videoconvert` 的 sham control，并记录最终帧的色彩格式、JPEG 质量、文件大小、清晰度和像素差。

此外：

- `exp2_B` 的最终帧实际是 320×240，并非“显示分辨率保持 640×480”；
- 中心裁剪同时改变视野、目标占比和构图，不能视为只减少细节；
- 320 采集再放大到 640 同时改变了传感器模式、插值和 JPEG 特征；
- 160 下采样再上采样改变的不只是纹理，也改变边缘、混叠和局部对比度。

因此 H2 当前可写为“多种降低高频细节或改变采集管线的处理与单词输出增加相关”，不能写成已确认唯一由“信息量”驱动。建议做同一冻结帧上的正交处理：高斯模糊、JPEG 质量、锐化、噪声、下/上采样，并加入所有管线 sham control。

### 7. H1、H2、H3、H4 的证据等级要整体下调

- **H1**：固定 512×512 预处理和近似恒定耗时与视觉 token 恒定相容，但耗时不是 token 数的直接测量。官方 SmolVLM 模型卡还说明较大图像在标准处理器中可能被划分为多个子图，因此必须把结论限定到本次 llama.cpp 实现。建议记录实际 image token 数或在源码中增加日志，再将“已证伪”改为“在当前实现和所测输入范围内不受支持”。
- **H2**：“描述先验激活”是潜在机制，不是已观测神经变量；当前只观察到句式分布变化。建议使用“与细节敏感的输出模板切换一致”，避免“直接证据”“完全一致”“强确认”。
- **H3**：只有同一家族的 256M 与 500M 两个点，且 mmproj/模型组件不同，不能推出“确定性随模型规模增强”。应改为“两个模型呈不同模式，是否由规模导致尚不确定”。
- **H4**：去掉 center 后没有恢复，可以反驳这个特定变体的简单预测，但不能“证伪所有位置冲突机制”；措辞同时改变句法和任务模板。改为“未支持原始 H4 的简单版本”。

### 8. 修正可直接核查的数据与叙述矛盾

除上述指标问题外，至少还要修正：

- §3.4 写 `max_tokens=32`，但 `llama_server.c` 和 `run_static_nocache.py` 都是 16；
- §4.2 称 500M@800 和 @1280 语义均为 100%，日志分析分别是 25 yes / 0 no / 2 unknown 与 26 yes / 0 no / 1 unknown；
- §4.8 表中 500M@temp=1.0 有 3/28 单词输出，正文却写“与温度完全无关”；更准确的说法是 t≤0.5 均为 0%，t=1.0 出现少量单词且语义 unknown 明显增加；
- §6.1 第 1 条写“与 prompt 强度/措辞无关”，但 §4.4 和 §4.11 的核心结论恰恰是措辞影响显著；
- 文首状态写 v0.3，下面已有 v0.4 更新；投稿稿应删除整个版本更新区；
- §3.5 仍称“三组实验”，表格也没有覆盖实验 2/3、7、D×分辨率和静态无缓存；
- §4.7 的“静态图不可信”与 §4.12 的无缓存复核重复且叙述阶段不同，应合并成一节；
- “实时推理”容易让人理解为实时帧率，而当前约 0.15–0.18 FPS；建议用“在线相机链路”或“实时采集、低帧率推理”。

## 三、最值得补做的实验（按优先级）

### 第一优先级：数据完整性与主效应复现

1. 修复指标脚本，自动输出 `format_word / semantic_label / semantic_correct / yes_rate / unknown_rate`；
2. 恢复并分开保存两份实验 5 A 日志，重算所有表格、置信区间和校正后 p 值；
3. 做 5–10 个独立 session 的随机区组复现，每个处理前后插入 A 基线；
4. 在每个 session 内混合正样本和负样本，避免把 Yes 先验当成识别能力；
5. 预注册主要终点为 `format_word`，次要终点为 `semantic_correct`。

### 第二优先级：闭合静态/动态与模糊机制

1. 使用同一批冻结帧做静态/程序路径的逐帧配对；
2. 构造帧差梯度，而不是只比较“一张静态图”和“实时序列”；
3. 增加双 `videoconvert` 的零模糊对照；
4. 对同一帧正交扫描 blur、JPEG quality、噪声、锐化和下/上采样；
5. 直接记录视觉 token 数、预处理后图像张量尺寸及首 token logprobs。

### 第三优先级：证明工程价值和外部有效性

1. 增加 llama.cpp grammar/logit mask 的强制 `yes|no` 解码基线，同时报告语义准确率和延迟；
2. 对比原生 Hugging Face Transformers 推理，区分模型现象与 llama.cpp/模板实现现象；
3. 至少增加 3–5 类物体、多个正负场景和不同位置；
4. 增加 F16 或更高精度权重，检验 Q8_0 是否参与现象；
5. 若资源允许，再加入其他模型家族。跨模型比单纯再加一个 SmolVLM 尺寸更有价值。

其中最实用的工程实验是受限解码：若语法约束能把格式稳定到 100%，且不降低正负样本语义准确率，论文就能从“现象报告”升级为“发现 + 可验证修复方案”。目前只提出 constrained decoding，但没有实际结果。

## 四、论文结构和写作优化（P1）

### 1. 收窄题目和核心 claim

当前题目把现象写成一般的小 VLM 规律，但证据只来自单设备、单引擎实现、单模型家族和单场景。可考虑：

- **Format-Compliance Instability in Edge-Deployed Small Vision-Language Models: A Controlled SmolVLM Case Study**
- **Capture Resolution and Input-Pipeline Sensitivity of Yes/No Format Compliance in SmolVLM on RK3588**
- 中文：**RK3588 上 SmolVLM 的 Yes/No 格式遵循对采集分辨率与输入链路的敏感性**

标题中用 `instability` 或 `transition` 比 `collapse` 更中性，也更符合跨会话存在较大波动的事实。

### 2. 摘要大幅压缩

当前摘要几乎容纳了全部实验，信息过载且含多个未闭合机制结论。建议控制为四部分：

1. 问题与平台；
2. 主观察（格式率与语义输出分离）；
3. 两个最可靠的干预结果；
4. 局限与工程启示。

摘要中暂时删除“必要条件”“确定性随规模增强”“强烈支持描述先验激活”等机制词，待跨 session 与配对对照完成后再恢复。

### 3. 把“结果”和“解释”分开

结果段只描述可观测量：单词率、句子率、Yes/No/unknown、延迟、置信区间。把“看不清”“信息过载”“诚实”“描述欲望”“能力竞争”等解释移入 Discussion，并标为假设。

建议把结果组织为：

1. 分辨率 × 模型；
2. session 变异；
3. 温度和措辞；
4. 图像处理干预；
5. 静态/序列输入；
6. 受限解码修复。

### 4. 增加三张关键图

- 分辨率 × 模型的 `format_word` 折线图，带 session/区组点和 95% CI；
- 模糊强度下 `format_word` 与 `semantic_correct` 双指标图，清楚展示“格式保持而语义转 No”；
- 各 session 基线的散点/森林图，直接展示 9%–67% 的会话漂移。

如果完成同帧实验，再增加“固定帧 → 受控 JPEG/噪声变化 → 输出形态”的配对转移图。

### 5. 工程建议不要超出数据范围

当前推荐“σ∈[1,4] 语义无损”过强：σ=3 的 Yes 率只有 87.5%，σ=4 为 93.5%，且只有一个正样本场景。建议改为：“在本次单场景会话中，σ=1–2 保持了 32/32 肯定语义并消除了句子输出；跨场景部署前仍需验证。”

同理，不能把 320×240 笼统推荐为最可靠方案，因为 500M@320 的 Yes 率曾在不同会话为 41% 和 95%。工程上更稳妥的主建议应是：**受限解码 + 独立语义验证 + 输入分布监控**，而不是固定一个分辨率或 blur 参数。
