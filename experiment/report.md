# 实验对比报告：SmolVLM-256M vs SmolVLM-500M（RK3588 板端）

> 报告日期：2026-08-07
> 平台：RK3588S (Debian 11, 192.168.1.8) · CPU 推理 (llama.cpp v0.15.3)
> 方法：main 主程序 (`rk3588-vlm`) 连续采集 320×240 实时帧，每帧完整推理，10 轮
> 任务：`Is there a black industrial fan in the center of the image? Please answer only yes or no.`
> 画面：黑色工业风扇（两模型共用同一场景）

---

## 1. 测试条件一致性

| 条件 | 256M | 500M | 一致性 |
|------|------|------|--------|
| 程序 | rk3588-vlm (main v3) | 同左 | ✅ |
| 分辨率 | 320×240 | 320×240 | ✅ |
| 间隔 | 1s | 1s | ✅ |
| Prompt | 相同 | 相同 | ✅ |
| 相机 | /dev/video22 | /dev/video22 | ✅ |
| 场景 | 工业风扇 | 工业风扇 | ✅ |
| 采样方式 | 实时新帧（无 KV cache） | 同左 | ✅ |

## 2. 核心数据对比

| 指标 | 256M | 500M | 差异 |
|------|------|------|------|
| **平均单帧耗时** | **5.49s** | **6.18s** | 256M 快 **11.2%** |
| 首轮耗时 | 5.91s | 7.40s | 256M 快 1.49s |
| 稳态范围（#2-#10） | 5.40-5.50s | 6.14-6.22s | 256M 波动更小 |
| 标准差 | ~0.15s (<3%) | ~0.03s (<1%) | 500M 更稳定 |
| 等效帧率 | 0.18 FPS | 0.16 FPS | — |
| 识别率 | **10/10 (100%)** | **9/10 (90%)** | 256M 更高 |
| 模型体积 | 167MB | 417MB | 256M 小 60% |
| 内存占用（估） | ~0.5GB | ~1GB | 256M 更省 |

## 3. 逐轮耗时明细

## 4. 结论

### 4.1 速度
- 256M 单帧 5.49s vs 500M 单帧 6.18s → **256M 快约 11%**
- 差距小于预期（模型参数少 50%，但耗时主要被 **图片编码 ~4.5s 锁死**，生成阶段只占 1-1.7s）
- **瓶颈是视觉编码器，不是 LLM 生成**：想显著提速需优化图像预处理（如降低 patch 数/编码分辨率）

### 4.2 准确率
- 256M：10/10 (100%)；500M：9/10 (90%，第 5 轮误判 NO)
- 单一简单任务上 256M 反而更稳；500M 仍有偶发误判

### 4.3 资源
- 256M 体积/内存约为 500M 的 40-50%，对 /userdata 空间（当前剩 2.3G）和内存更友好

### 4.4 建议
| 场景 | 推荐 |
|------|------|
| 简单 yes/no 检测（本类任务） | **256M**：更快、更准、更省资源 |
| 需要复杂描述/多目标推理 | 500M（需更多测试验证） |
| 实时检测（<1s/帧） | 两者都不达标 → 需 YOLO+NPU 方案（另议） |

## 5. 附注

- 固定图片 + llama-server 的 KV cache 加速（0.1s/次）**不适用于逐帧检测**，已用 main 主程序实测排除

# 第二轮实验 (v2)：640×480 分辨率对比

> 第二轮：分辨率提升到 640×480，其余条件与第一轮完全一致（同程序/prompt/场景/间隔）
> 实验日期：2026-08-07 · 详细数据：`experiment-smolvlm256-v2.md` / `experiment-smolvlm500-v2.md`

## 6. v2 核心数据

| 指标 | 256M @640×480 | 500M @640×480 |
|------|--------------|--------------|
| 平均耗时 | 5.69s | 6.67s |
| 程序判定识别率 | 10%（1/10） | 0%（0/10） |
| **语义判定识别率** | **90%**（#7 corner 存疑） | **100%** |
| 输出格式 | 90% 完整句子 | 100% 完整句子 |
| 等效帧率 | 0.18 FPS | 0.15 FPS |

### v2 关键发现

1. **输出格式漂移（两模型一致）**：640×480 下模型不再输出严格 "Yes."，而是输出完整描述句（"There is a black industrial fan..." / "A black industrial fan is in the foreground..."）——语义正确但 `parse_yes_no` 只认单词，全部判 -1
2. **这是解析器兼容性问题，不是识别失败**：语义上 256M 9/10、500M 10/10 都正确确认了风扇存在
3. 500M 在 640×480 下表述为 "foreground"（前景）而非 "center"——高分辨率下风扇占画面比例大，模型给出更具体位置描述

# 综合对比报告：4 组实验汇总（SmolVLM-256M/500M × 320×240/640×480）

## 7. 四组数据总览

| # | 模型 | 分辨率 | 平均耗时 | 程序判定识别率 | 语义识别率 | 输出合规 |
|---|------|--------|---------|--------------|-----------|---------|
| 1 | 256M | 320×240 | **5.49s** | 100% (10/10) | 100% | ✅ 严格 yes/no |
| 2 | 500M | 320×240 | 6.18s | 90% (9/10) | 90% | ✅ 严格 yes/no |
| 3 | 256M | 640×480 | 5.69s | 10% (1/10) | 90% | ❌ 完整句子 |
| 4 | 500M | 640×480 | 6.67s | 0% (0/10) | 100% | ❌ 完整句子 |

## 8. 维度分析

### 8.1 速度（耗时）

| 对比 | 差异 |
|------|------|
| 256M vs 500M @320 | 5.49 vs 6.18s → 256M 快 11% |
| 256M vs 500M @640 | 5.69 vs 6.67s → 256M 快 15% |
| 320 vs 640 @256M | 5.49 vs 5.69s → 640 慢 4%（边际小） |
| 320 vs 640 @500M | 6.18 vs 6.67s → 640 慢 8% |

**结论**：
- 256M 始终比 500M 快 11-15%
- 分辨率翻倍（像素×4）只带来 4-8% 耗时增加 → **瓶颈不是像素数，而是编码管线固定开销（~4.5s）**

### 8.2 识别准确率

| 模型 | 320×240 | 640×480 |
|------|---------|---------|
| 256M | 100% (严格判定) | 90% (语义) |
| 500M | 90% (严格判定, 1 次误判 NO) | 100% (语义) |

- 320×240 下两模型都能输出严格 yes/no，256M 更稳（500M 有一次误判 NO）
- 640×480 下两模型都漂移为完整句子，程序判定近乎失效（需修解析器）

### 8.3 输出合规性（关键发现）

**分辨率影响模型输出格式**：
- 320×240 → 输出简短 "Yes."/"No."（prompt 约束生效）
- 640×480 → 输出完整句子（prompt 约束失效，模型"话变多"）

**原因推测**：高分辨率下模型看到更多细节，倾向于给出完整描述而非简单判断；SmolVLM 系小模型对 "answer only yes or no" 的指令遵循随输入变化。

**修复方向**：
1. 增强 `parse_yes_no`：识别 "There is a.../A ... is.../No.../Yes" 等完整句型（语义判断）
2. 或 prompt 末尾追加 `answer in a word: yes or no`（此前已验证可提升合规）
3. 或限制 `max_tokens` 到 2-3，物理上截断完整句子的生成

## 9. 最终结论与建议

| 场景 | 推荐 |
|------|------|
| 简单 yes/no 检测 | **256M @ 320×240**：最快 (5.49s) + 最合规 (100% 严格判定) + 最省资源 |
| 需要高分辨率细节 | 640×480（需先修解析器） |
| 复杂描述/多目标 | 500M（640×480 语义 100%，但需解析器增强） |
| 实时检测 (<1s/帧) | 都不达标 → 需 YOLO+NPU 方案（另议） |

**综合推荐**：
1. **首选 256M @ 320×240** —— 4 组实验中唯一"快 + 准 + 合规"全满足的配置
2. **下一优先级**：修复 `parse_yes_no` 支持完整句子（一行正则即可），修复后 640×480 配置可用
3. 分辨率对耗时的边际影响小，若应用需要细节，640×480 的成本可控（+4~8% 耗时）

# 第三轮实验 (v2-strict)：640×480 + 严厉 Prompt

> 第三轮：针对 v2 的输出格式漂移，改用严厉 prompt（`You must answer with exactly one word, either "yes" or "no". No other text, no punctuation, no explanation.`）重新测试 640×480
> 实验日期：2026-08-07 · 详细数据：`experiment-smolvlm256-v2-strict.md` / `experiment-smolvlm500-v2-strict.md`

## 11. v2-strict 核心数据

| 指标 | 256M @640 strict | 500M @640 strict |
|------|-----------------|-----------------|
| 平均耗时 | 5.74s | 6.58s |
| 程序判定识别率 | 10%（1/10） | **0%（0/10）** |
| 语义判定识别率 | **100%** | **100%** |
| 输出合规（严格 yes/no） | ❌ 1/10 | ❌ 0/10 |
| 等效帧率 | 0.17 FPS | 0.15 FPS |

### v2-strict 关键结论

1. **严厉 prompt 对 640×480 基本无效（两模型一致）**：
   - 256M：10 轮仅 1 轮 "Yes."（与 v2 非 strict 相同，无改善）
   - 500M：10 轮 0 轮 "Yes."（比 v2 更差）
2. **语义识别不受影响**：两模型 10/10 都正确确认风扇存在 → 识别能力无退化
3. **耗时不变**：与 v2 几乎相同（prompt 长度变化无影响）
4. **prompt 工程路线走不通**：SmolVLM 系模型在 640×480 下指令遵循失效，强化 prompt 无法恢复合规输出

# 综合对比报告：6 组实验汇总（2 模型 × 2 分辨率 × prompt 强弱）

## 12. 六组数据总览

| # | 模型 | 分辨率 | Prompt | 平均耗时 | 程序判定 | 语义识别 | 输出合规 |
|---|------|--------|--------|---------|---------|---------|---------|
| 1 | 256M | 320×240 | 普通 | **5.49s** | 100% | 100% | ✅ |
| 2 | 500M | 320×240 | 普通 | 6.18s | 90% | 90% | ✅ |
| 3 | 256M | 640×480 | 普通 | 5.69s | 10% | 90% | ❌ |
| 4 | 500M | 640×480 | 普通 | 6.67s | 0% | 100% | ❌ |
| 5 | 256M | 640×480 | 严厉 | 5.74s | 10% | 100% | ❌ |
| 6 | 500M | 640×480 | 严厉 | 6.58s | 0% | 100% | ❌ |

## 13. 最终结论

### 13.1 速度
- 256M 恒快于 500M（11-15%）：320 下 5.49 vs 6.18s；640 下 5.69 vs 6.67s
- 分辨率翻倍（像素×4）只慢 4-8% → 瓶颈是编码固定开销 ~4.5s
- **严格 prompt 不影响耗时**（5.69→5.74s / 6.67→6.58s，噪声级差异）

### 13.2 输出合规（本轮的焦点）
| 配置 | 合规率（严格 yes/no） |
|------|---------------------|
| **320×240（两模型）** | **90-100%** ✅ prompt 约束生效 |
| 640×480 普通 prompt | 0-10% ❌ 输出完整句子 |
| 640×480 严厉 prompt | 0-10% ❌ **无改善** |

**核心结论：合规性由分辨率决定，与 prompt 强弱无关。** 320×240 下 prompt 有效；640×480 下模型"话变多"，prompt 工程无法挽回。

### 13.3 识别准确率
- 语义层面：6 组全部 90-100% 正确识别风扇存在（仅 320 下 500M 有 1 次误判 NO）
- 模型本身识别能力稳定，问题只在输出格式解析

### 13.4 最终推荐（更新）
| 场景 | 推荐 |
|------|------|
| 需要合规输出（程序直接消费） | **256M @ 320×240**（唯一全满足） |
| 需要高分辨率细节 | 640×480 + **修复 `parse_yes_no`**（语义已 100%，只差解析） |
| 实时检测 (<1s/帧) | 都不达标 → YOLO+NPU 方案 |

**下一步建议（按优先级）**：
1. **修复 `parse_yes_no`**：识别 "There is a.../A ... is.../Yes/No" 等完整句型 → 640×480 立即可用（语义 100%）
2. 或限制 `max_tokens=2-3`（改 llama_infer 调用参数）→ 物理截断完整句子
3. 应用需要细节时用 640×480 + 修复后解析器；否则 320×240 已够用
